# План: приложение «Питание» (nutrition)

Второе мини-приложение суперапа: дневник питания с распознаванием еды по фото и тексту через LLM. Строится по рецепту из [PLATFORM.md](PLATFORM.md), раздел 4. Тема синяя, `appId` — `nutrition`.

## 1. Сценарии

1. **Первый запуск.** Ввожу пол, дату рождения, рост, вес и уровень активности. Приложение считает:
   - **BMR** — сколько калорий организм тратит за сутки в покое;
   - **TDEE** — расход с учётом активности;
   - **цель на день** — калории и норму белков, жиров и углеводов (БЖУ) под выбранную цель. По умолчанию цель — похудение, в настройках её можно сменить на поддержание или набор веса.

   Все цифры можно потом поправить вручную.

2. **Приём пищи по фото.** Фотографирую еду и пишу комментарий («плов, тарелка примерно как ладонь, без хлеба»). LLM распознаёт блюда, оценивает порцию в граммах, калории и БЖУ. Я проверяю и правлю результат, сохраняю, и он попадает в дневник за сегодня.
3. **Приём пищи текстом.** Без фото: «2 яйца, кусок хлеба, кофе с молоком». Дальше всё так же: распознавание, проверка, сохранение.
4. **Сегодня.** Сколько съедено и сколько осталось до нормы по калориям и БЖУ, список приёмов пищи.
5. **История.** Дни с итогами, вес во времени. Приёмы пищи подписываются по времени: «Завтрак», «Обед», «Ужин», «Перекус».

## 2. Расчёты

Формулы живут в одном модуле бэкенда (`nutrition/profile/energy.ts`) и покрыты юнит-тестами.

**BMR, формула Миффлина — Сан Жеора** (вес в кг, рост в см, возраст в годах):

- мужчины: `10 × вес + 6,25 × рост − 5 × возраст + 5`;
- женщины: `10 × вес + 6,25 × рост − 5 × возраст − 161`.

Хранится дата рождения, а не возраст: так возраст считается на текущую дату и не устаревает.

**TDEE = BMR × коэффициент активности:**

| Уровень                                     | Коэффициент |
| ------------------------------------------- | ----------- |
| Сидячий образ жизни                         | 1,2         |
| Лёгкая активность (1–3 тренировки в неделю) | 1,375       |
| Средняя (3–5)                               | 1,55        |
| Высокая (6–7)                               | 1,725       |
| Очень высокая (физический труд + спорт)     | 1,9         |

**Цель** выбирается в настройках, по умолчанию «Похудение»:

| Цель                     | Калории                           | Белок       | Комментарий                  |
| ------------------------ | --------------------------------- | ----------- | ---------------------------- |
| Похудение (по умолчанию) | TDEE − 20% (настраивается 10–25%) | 1,8 г на кг | ~0,5–0,7 кг в неделю         |
| Поддержание              | TDEE                              | 1,6 г на кг |                              |
| Набор массы              | TDEE + 10% (настраивается 5–15%)  | 1,8 г на кг | медленный набор, меньше жира |

- **Нижняя граница калорий при похудении:** не меньше BMR и не меньше 1500 ккал для мужчин и 1200 ккал для женщин. Если дефицит уводит ниже, используется граница, а интерфейс показывает почему.
- **Жиры** — 0,9 г на кг для всех целей.
- **Углеводы** — остаток калорий (4 ккал в 1 г белка или углеводов, 9 ккал в 1 г жира).
- При смене цели или веса цели пересчитываются, ручные значения сохраняются (см. ниже).

**Ручные правки.** В профиле хранятся и рассчитанные значения, и ручные. Если я поменял цель вручную, она не перезаписывается при изменении веса. Кнопка «Пересчитать» сбрасывает ручные значения на рассчитанные.

## 3. Распознавание еды через LLM

### 3.1 Поток данных

```
Mini App: фото (камера) + комментарий
   │  POST /api/nutrition/meals/analyze  (multipart)
   ▼
API: проверка → сжатие фото (sharp: ≤1568px, JPEG, без EXIF) → сохранение фото на диск
   │
   ▼
MealAnalyzer (выбранный провайдер: Claude / Gemini / OpenAI)
   картинка + комментарий + системный промпт → JSON по общей схеме
   │
   ▼
API: черновик приёма пищи (status = draft) со списком блюд → ответ клиенту
   │
   ▼
Mini App: экран проверки — правлю граммы и названия, удаляю лишнее → «Сохранить» (status = confirmed)
```

Черновик обязателен: оценка порции по фото всегда приблизительная, поэтому в дневник ничего не попадает без моей проверки. Если что-то не так, можно дописать уточнение («порция в два раза больше») и запустить анализ ещё раз.

### 3.2 Независимость от провайдера

Приложение не привязано к одному провайдеру LLM. Всё, что не зависит от него, общее, а под каждого провайдера пишется небольшой адаптер:

```
nutrition/analysis/
  meal-analyzer.ts          интерфейс MealAnalyzer + токен для DI
  meal-analysis.schema.ts   zod-схема результата (общая для всех провайдеров)
  meal-analysis.prompt.ts   системный промпт и сборка текста запроса (общие)
  analysis.module.ts        выбирает адаптер по NUTRITION_LLM_PROVIDER
  providers/
    claude.analyzer.ts      @anthropic-ai/sdk
    gemini.analyzer.ts      официальный SDK Google Gen AI
    openai.analyzer.ts      официальный SDK OpenAI
```

**Интерфейс:**

```ts
interface MealAnalysisInput {
  comment: string;
  photo?: { data: Buffer; mediaType: "image/jpeg" };
  clarification?: string; // уточнение при повторном анализе
}

interface MealAnalyzer {
  analyze(input: MealAnalysisInput): Promise<MealAnalysisResult>;
}

// Результат одинаковый для всех провайдеров (zod-схема в meal-analysis.schema.ts)
type MealAnalysisResult = {
  items: {
    name: string;
    grams: number;
    kcal: number;
    protein: number;
    fat: number;
    carbs: number;
    confidence: "low" | "medium" | "high";
  }[];
  assumptions: string[]; // что предположено: «масло при жарке ~10 г»
  questions: string[]; // что стоит уточнить
  meta: { provider: string; model: string; inputTokens: number; outputTokens: number };
};
```

**Правила:**

- **Сервисы приёмов пищи** зависят только от интерфейса `MealAnalyzer` (через DI-токен) и ничего не знают о провайдерах.
- **Адаптер отвечает только за своего провайдера:**
  - превращает `MealAnalysisInput` в запрос: картинка в формате провайдера, текст, системный промпт;
  - включает у провайдера режим строгого JSON по схеме;
  - превращает ответ и ошибки провайдера в `MealAnalysisResult` или в понятную русскую ошибку.
- **Сервер всегда проверяет ответ** общей zod-схемой, у любого провайдера.
- **Промпт и схема общие.** Если провайдер требует JSON Schema, она генерируется из zod-схемы, чтобы не держать два описания.
- **Выбор провайдера — через окружение:**

  ```
  NUTRITION_LLM_PROVIDER=claude        # claude | gemini | openai
  NUTRITION_LLM_MODEL=claude-opus-5-5  # имя модели у выбранного провайдера
  ANTHROPIC_API_KEY=...                # ключ нужен только для выбранного провайдера
  GEMINI_API_KEY=...
  OPENAI_API_KEY=...
  ```

  `readConfig()` проверяет, что для выбранного провайдера задан ключ.

- **Провайдер и модель записываются** в `Meal.analysis.meta` вместе с расходом токенов, чтобы сравнивать качество и стоимость.
- **Новый провайдер** = новый файл в `providers/` и одна строка в выборе адаптера.
- **Реализация по этапам.** На этапе 2 делаем один адаптер (Claude) и сразу проверяем, что интерфейс не протекает. Остальные адаптеры добавляются, когда понадобятся. Набор тестовых фото из этапа 5 позволяет сравнить провайдеров на своих данных.

**Общие требования к любому адаптеру:**

- **Таймаут** запроса до 60 с. Клиент всё это время показывает «Анализируем…».
- **Повтор** при временных ошибках (429, 5xx). Ошибки валидации не повторяются.
- **Лимит частоты** для `/meals/analyze` отдельный, строже общего.
- **Ключи** провайдеров хранятся только на сервере.

**Особенности адаптера Claude** (первый адаптер):

- **Модель** `claude-opus-5-5`.
- **Картинка** — блок `image` с `source: { type: "base64", ... }`.
- **JSON** через `output_config.format`.
- **Глубина рассуждения:** `output_config.effort`, начинаем с `medium`.
- **Кеш промпта:** `cache_control` на системный промпт.
- **Отказ модели:** проверять `stop_reason`, подключить серверный фолбэк `fallbacks: "default"`.

### 3.3 Примерная стоимость

Зависит от провайдера и модели. Для `claude-opus-5-5` ($4 за 1M входных токенов, $20 за 1M выходных, чтение из кеша $0,20 за 1M) оценка на один анализ такая:

- фото ~1,5k токенов, промпт ~1–2k (большая часть из кеша), текст ~100;
- ответ с рассуждением ~1–2k токенов.

Получается **около $0,03–0,05 за приём пищи**, то есть **$4–6 в месяц** при 4 приёмах в день. Реальный расход по каждому провайдеру видно в `Meal.analysis.meta`.

## 4. Хранение фото

Решение: **диск сервера** (Docker volume), хранить **бессрочно**.

- **В коде** интерфейс `PhotoStorage` (`put`, `get`, `delete`) и одна реализация `LocalPhotoStorage`. Если позже понадобится MinIO или облако, добавится `S3PhotoStorage` без изменений в остальном коде.
- **Папка** задаётся через `PHOTO_STORAGE_DIR` (например, `/data/photos`). В `docker-compose.yml` к ней подключается именованный volume `nutrition_photos`, чтобы фото переживали пересборку контейнера.
- **Формат файла:** сжатое фото (≤1568px, JPEG ~80%, без EXIF, чтобы не хранить геолокацию) плюс миниатюра ~400px для списков.
- **Ключ:** `nutrition/<ownerId>/<yyyy>/<mm>/<uuid>.jpg`.
- **Доступ:** клиент получает фото через `GET /api/nutrition/photos/:id` с проверкой владельца, прямых ссылок на файлы нет.
- **Бэкап:** volume с фото нужно добавить в бэкап вместе с PostgreSQL.

## 5. Модель данных (Prisma)

```prisma
model NutritionProfile {
  ownerId        String   @id @db.Uuid          // один профиль на владельца
  sex            String                          // male | female
  birthDate      DateTime @db.Date
  heightCm       Int
  weightKg       Decimal  @db.Decimal(5, 1)
  activityLevel  String                          // sedentary | light | moderate | high | very_high
  goal           String   @default("lose")       // lose | maintain | gain — выбирается в настройках
  deficitPercent Int      @default(20)           // для похудения, 10–25
  surplusPercent Int      @default(10)           // для набора, 5–15
  // Рассчитанные значения хранятся на момент последнего пересчёта; *Override — ручные правки
  bmrKcal        Int
  tdeeKcal       Int
  targetKcal     Int
  targetProteinG Int
  targetFatG     Int
  targetCarbsG   Int
  overrides      Json     @default("{}")         // какие цели заданы вручную
  updatedAt      DateTime @updatedAt
}

model WeightEntry {
  id       String   @id @default(uuid()) @db.Uuid
  ownerId  String   @db.Uuid
  date     DateTime @db.Date
  weightKg Decimal  @db.Decimal(5, 1)
  @@unique([ownerId, date])
}

model Meal {
  id             String    @id @default(uuid()) @db.Uuid
  ownerId        String    @db.Uuid
  eatenAt        DateTime  @db.Timestamptz(3)    // название приёма считается по этому времени
  source         String                          // photo | text | manual
  status         String    @default("draft")     // draft | confirmed
  comment        String    @default("")          // мой комментарий к еде
  photoId        String?   @db.Uuid
  // Итоги по блюдам, денормализованы для быстрых сводок за день
  kcal           Decimal   @db.Decimal(7, 1)
  proteinG       Decimal   @db.Decimal(6, 1)
  fatG           Decimal   @db.Decimal(6, 1)
  carbsG         Decimal   @db.Decimal(6, 1)
  analysis       Json?                            // assumptions, questions, meta: provider, model, токены
  version        Int       @default(1)
  idempotencyKey String
  createdAt      DateTime  @default(now())
  deletedAt      DateTime?
  items          MealItem[]
  @@unique([ownerId, idempotencyKey])
  @@index([ownerId, eatenAt])
}

model MealItem {
  id         String  @id @default(uuid()) @db.Uuid
  mealId     String  @db.Uuid
  meal       Meal    @relation(fields: [mealId], references: [id], onDelete: Cascade)
  position   Int
  name       String
  grams      Decimal @db.Decimal(6, 1)
  kcal       Decimal @db.Decimal(7, 1)
  proteinG   Decimal @db.Decimal(6, 1)
  fatG       Decimal @db.Decimal(6, 1)
  carbsG     Decimal @db.Decimal(6, 1)
  confidence String? // low | medium | high — от LLM
}

model MealPhoto {
  id         String   @id @default(uuid()) @db.Uuid
  ownerId    String   @db.Uuid
  storageKey String
  thumbKey   String
  createdAt  DateTime @default(now())
}
```

Все модели связаны с `Owner` (в схеме нужны `@relation`, здесь опущены для краткости). «Сегодня» считается в часовом поясе владельца (`Owner.timezone`), как в кошельке.

**Название приёма пищи** не хранится, а вычисляется по `eatenAt` в часовом поясе владельца:

| Время                                                                                 | Название |
| ------------------------------------------------------------------------------------- | -------- |
| 05:00–10:59                                                                           | Завтрак  |
| 11:00–15:59                                                                           | Обед     |
| 16:00–21:59                                                                           | Ужин     |
| 22:00–04:59 и всё, что между основными приёмами, если в этом интервале уже есть приём | Перекус  |

Правило: первый приём в интервале получает его название, следующие в том же интервале — «Перекус». Если у приёма есть фото, к названию добавляется первое блюдо: «Обед · Плов». Границы — константы в одном месте фронтенда (`lib/meal-names.ts`), их легко поменять.

## 6. API (`/api/nutrition/...`)

| Метод и путь                               | Назначение                                                                          |
| ------------------------------------------ | ----------------------------------------------------------------------------------- |
| `GET /profile`                             | профиль и цели или `null`, если онбординг не пройден                                |
| `PUT /profile`                             | сохранить данные и цель, пересчитать BMR, TDEE и цели (ручные значения сохраняются) |
| `POST /profile/recalculate`                | сбросить ручные цели на рассчитанные                                                |
| `POST /meals/analyze`                      | multipart: `photo?`, `comment`, `eatenAt` → черновик. Заголовок `Idempotency-Key`   |
| `POST /meals/:id/reanalyze`                | повторный анализ с уточнением                                                       |
| `POST /meals`                              | ручной ввод без LLM                                                                 |
| `PATCH /meals/:id`                         | правка блюд и полей (с `version`)                                                   |
| `POST /meals/:id/confirm`                  | черновик → дневник                                                                  |
| `DELETE /meals/:id`                        | удалить (мягко)                                                                     |
| `GET /days/:date`                          | приёмы пищи за день, итоги, цели, остаток                                           |
| `GET /days?from&to`                        | итоги по дням для истории и графиков                                                |
| `POST /weight`, `GET /weight?from&to`      | вес                                                                                 |
| `GET /photos/:id`, `GET /photos/:id/thumb` | фото с проверкой владельца                                                          |

Структура бэкенда — `apps/api/src/nutrition/`:

- `nutrition.module.ts`;
- `profile/` (с `energy.ts`);
- `meals/`, `days/`, `weight/`;
- `analysis/` (интерфейс `MealAnalyzer` и адаптеры провайдеров, см. 3.2);
- `photos/` (`PhotoStorage`, `LocalPhotoStorage`).

Новые зависимости: `sharp`, SDK выбранных провайдеров LLM (сначала `@anthropic-ai/sdk`).

## 7. Фронтенд (`apps/nutrition-web`)

Синяя тема, общий код из `@ui`. Вкладки:

1. **Сегодня.** Кольцо калорий («съедено N из M, осталось K»), три полосы БЖУ, приёмы пищи с названиями по времени («Завтрак · 08:40»). Большая кнопка «+» открывает выбор: «Фото» или «Текстом».
2. **История.** Дни с итогами и отметкой, укладываюсь ли в цель; график веса.
3. **Профиль.** Мои данные; **цель** (похудение / поддержание / набор) и её темп (% дефицита или профицита); нормы (с пометкой «вручную»), кнопка «Пересчитать»; добавление веса.

Ещё нужны:

- **Онбординг** — шаги при первом запуске: пол и дата рождения → рост и вес → активность → итоговые цифры, которые можно сразу поправить. Цель по умолчанию «Похудение», сменить её можно в профиле.
- **Добавление еды:**
  - снимок через `<input type="file" accept="image/*" capture="environment">`, это работает в Telegram WebView;
  - предпросмотр и комментарий;
  - экран «Анализируем…»;
  - экран проверки: список блюд с полями граммов (пересчёт КБЖУ пропорционально), удаление и добавление блюда, предположения модели, кнопки «Уточнить» и «Сохранить».
- **Новые компоненты в `@ui`**, если понадобятся и кошельку: прогресс-кольцо, полоса прогресса, пошаговая форма.

## 8. Этапы

1. **Фундамент.**
   - Модули `nutrition/` (профиль, цели и расчёты для всех трёх целей с тестами), миграция.
   - Фронтенд `apps/nutrition-web`: синяя тема, онбординг, «Сегодня» с целями и пустым дневником.
   - Docker-сервис, кнопка в боте.
2. **Ввод текстом.**
   - Интерфейс `MealAnalyzer`, общая схема и промпт, первый адаптер (Claude), выбор провайдера через окружение.
   - Черновик → проверка → дневник, итоги за день.
   - Ручной ввод.
3. **Фото.**
   - `PhotoStorage` на диске (volume `nutrition_photos`), сжатие через sharp.
   - Анализ по фото, миниатюры в дневнике.
4. **История и вес.** Сводки по дням, график веса, пересчёт целей при новом весе.
5. **Качество распознавания.**
   - Собрать 20–30 своих фото с проверенными данными (взвешенные порции).
   - Прогонять их при смене промпта, провайдера или модели и следить за ошибкой по калориям.
   - Адаптеры Gemini и OpenAI — по необходимости, чтобы сравнить провайдеров на этом наборе.

## 9. Принятые решения

| Вопрос                 | Решение                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| Провайдер LLM          | не привязываемся: интерфейс `MealAnalyzer` + адаптеры, выбор через `NUTRITION_LLM_PROVIDER`; первый — Claude |
| Хранилище фото         | диск сервера (Docker volume), через интерфейс `PhotoStorage`                                                 |
| Срок хранения фото     | бессрочно                                                                                                    |
| Типы приёмов пищи      | не храним; название вычисляется по времени (раздел 5)                                                        |
| Цели                   | похудение (по умолчанию), поддержание, набор — выбор в профиле                                               |
| Вода, шаги, тренировки | отложено                                                                                                     |
